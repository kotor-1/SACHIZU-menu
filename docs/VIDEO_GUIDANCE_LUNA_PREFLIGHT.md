# Luna provider preflight (offline preparation)

`LunaCanaryControlPlane` is the server entrypoint. It uses the Phase 2 authenticated identity and the `ANALYZE_VIDEO_GUIDANCE` owner grant, then the Phase 3 SQLite claim, global work identity, reservation, attempt, lease and fence. There is no enabled route, execution CLI, key lookup or automatic model fallback. The provider defaults to `NETWORK_DISABLED`; only explicitly injected test transport bypasses that default, in `NODE_ENV=test`.

The sole model is `gpt-6-luna`. Canary-0 is exercise `cmtrg8ip20056itxbl2ouptrx`: 12 private JPEG frames, 1280×720, high detail, fixed source timestamps, medium reasoning, strict `luna-visual-guidance-v1`, prompt `luna-frame-observation-v1`. One canonical builder produces the Responses body and the documented input-token endpoint projection. Shared model/instructions/input/images/order/schema/reasoning are identical. The receipt binds the complete response payload hash and frame manifest hash, including response-only controls.

Controls: `max_output_tokens=8192` (reasoning included), `service_tier=default`, `prompt_cache_options={mode:"explicit"}` with zero breakpoints, `store=false`, `background=false`, `stream=false`, no tools, no truncation, no SDK, no redirects and zero retries. Deadline: 120 seconds; lease: 180 seconds; heartbeat: 15 seconds. Input requests are at most 16 MiB; raw response bodies at most 1 MiB. The output cap is a billing bound, not a guarantee that every maximum-length schema fixture plus reasoning fits. Incomplete output stops without repair calls.

The token count and response are separate durable gates/counters, each capped at one. `TOKEN_COUNT_ONLY` cannot send an inference. `countInputTokens()` targets `POST /v1/responses/input_tokens`; `createResponse()` targets `POST /v1/responses`. Neither operation is authorized by this implementation task. A later explicit authorization is required for each gate. API keys are server-only constructor secrets, never part of payloads/raw/reports.

The operator-approved response policy fixes an exact decimal USD cap, manifest hash and freshly checked official PriceSnapshot before creating the single-item batch. That immutable policy cannot be enlarged by changing environment variables. Unknown token counts/caps, expired receipts, mismatched hashes/models/prices, absent permissions and disabled networking fail closed. Prices must be rechecked against the official pricing page immediately before execution; the maximum accepted snapshot/receipt age is 24 hours. The final cost gate is checked again synchronously before transport invocation.

Standard global prices checked on 2026-10-05: at up to 272,000 input tokens, uncached/cached/cache-write/output are $0.10/$0.01/$0.125/$0.50 per million tokens. Above that threshold they are $0.20/$0.02/$0.25/$0.75, for the full request. No-cache upper bound is `N*input_rate/1e6 + 8192*output_rate/1e6`. Accounting uses integer nanoUSD and rounds the combined bound upward to microUSD. Reasoning is a subset of output and is not charged twice. Missing usage is unknown, never zero; reservations remain held.

Raw bytes are fsynced to an explicit `LOCAL_PRIVATE` directory (`video-guidance-raw/<dispatchKey>.raw`), followed by allowlisted metadata. Header checkpoints retain `x-request-id` even if body reading fails. Authorization headers are not persisted. Directories/files are 0700/0600; public paths and symlinks are rejected. Request IDs are distinct: deterministic `X-Client-Request-Id` is `vg-` plus SHA-256 of operation and durable dispatch key; `x-request-id` is the real response header or null; body Response ID is captured separately.

After ambiguous send, UNKNOWN blocks all automatic resend and keeps budget reserved. Header-only recovery copies an existing local checkpoint into the ledger without resolving UNKNOWN. With complete local raw, an authenticated explicit recovery after lease expiry adopts the same immutable bytes, and processing resumes with zero network requests. Raw-only orphans without trustworthy metadata stay quarantined; the low-level orphan adoption operation requires verified dispatch metadata. No automatic retrieval request exists. `store=false` does not promise zero provider retention or retrievability; a future retrieval policy requires a separate authorization/counter.

Successful parsing stores neutral observations and an Exercise-specific `AI_ANALYZED` candidate on the attempt. It creates no Guidance revision/head/audit and cannot change `approvedRevisionId`, `latestCandidateRevisionId`, or the effective Guidance. Promotion/mapping remains a separate authorized operation. PARTIAL is technical success. Unknown fields, malformed JSON, missing output, incomplete responses and invalid schemas retain raw/usage and stop.

Run tests only in a disposable repository copy with isolated generated Prisma client and DB. Before the isolation guard, Vitest global setup rebuilt `prisma/test.db`. The prior validation accidentally reset that original DB once; it was restored byte-for-byte. See the Phase 5.1 safety report. Offline technical tests alone do not grant commit or API execution readiness.

Clean revalidation adds a mandatory guard before Vitest setup. Set `SACHIZU_TEST_ISOLATION_ROOT` to an existing dedicated temporary directory, `SACHIZU_ORIGINAL_WORKSPACE_ROOT` to the protected repository, `DATABASE_URL` to an absolute `file:` URL inside that temporary directory (for example `databases/main-suite.sqlite`), and `TMPDIR` to a scratch directory inside it. No DB URL defaults remain. Missing isolation, original paths, `dev.db`/`test.db`, relative URLs, symlink escapes and paths outside the isolated root are rejected before deletion or connection. Migration/snapshot harnesses can preload `tests/support/assert-isolated-environment.ts` through `node --import tsx --import ...`. The clean validation also denies original-tree writes at OS level for all child processes, including native Prisma engines. The prior incident remains in reports; a successful subsequent clean validation can authorize a scoped commit, but no external API execution.
